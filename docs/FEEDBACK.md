# Builder Feedback on Developing with XO

I built Layaway Jar, an on-chain recurring savings covenant on Bitcoin Cash using the XO template framework. Traditional layaway relies on merchant custody and physical ledgers, while generic savings apps offer no programmable guarantees. Layaway Jar enforces an autonomous escrow where balance equals UTXO value. A saver deposits incrementally toward a fixed purchase target. When reached, the covenant atomically releases the target to the merchant and refunds excess to the saver; otherwise, the saver can refund at any time.

XO's programmatic abstractions are well-structured. Creating actions via Engine.create, compiling templates with parseTemplate, and exporting portable invites with serializeInvitation worked seamlessly across distinct environments. Reusing the derived saverKey across multiple follow-up actions (createJar -> deposit -> release) felt clean, allowing sequential UTXO transitions without bespoke account orchestration. The deterministic nature of template identifiers—where parseTemplate and importTemplate hash to the exact same content-addressed ID—made fixture validation reliable. Combining P2SH32 with Libauth's local BCH VM execution allowed us to verify every spend path locally before network broadcast. Both the release path and the covenant-enforced refund script executed on Chipnet without script evaluation failures on our first broadcast attempts.

We encountered two friction points:
First, fee estimation severely undershoots for P2SH32 inputs. estimateTransactionFee does not account for the substantial redeem script size inside the unlocking bytecode. A multi-step deposit transaction was estimated far too low, resulting in insufficient fee errors that forced us to implement manual vsize measurement and retry wrappers. Repro: Construct a deposit input referencing a P2SH32 covenant outpoint; compare the engine's estimated vsize against the finalized serialized transaction vsize.
Second, selectable: false is ignored for Electrum UTXOs. In our template, the covenant output is explicitly flagged selectable: false to prevent accidental inclusion in regular payments. However, toUnspentOutputData marks every Electrum UTXO selectable: true. Consequently, listSpendableUnspentOutputs exposes the covenant UTXO, causing standard engine operations to attempt spending it. Repro: Synchronize an engine wallet holding a jar covenant outpoint and inspect the spendable outputs array.

The official guides and blog posts provided a fast on-ramp, enabling us to assemble a four-action template in a single working session. However, understanding the exact lifecycle of serialized invitations and using the blaze.xo.cash debug tool required inspecting runtime output rather than reading docs. Specifically, the debug tool requires explicitly importing the template JSON before an invitation can resolve; otherwise, it throws a missing template error. Clarifying this prerequisite in the onboarding guide would prevent confusing debugging cycles.

I recommend three improvements: First, update fee estimation algorithms to inspect actual unlocking bytecode lengths for P2SH32 covenants or expose explicit fee override hooks. Second, strictly enforce the selectable flag across Electrum UTXO ingest. Third, enforce strict runtime typing on stored covenant state objects so numerical satoshi amounts never inadvertently serialize into strings across multi-step invitation flows.

Yes. For well-scoped smart covenants requiring multi-stage follow-up actions and deterministic spend paths, XO offers a coherent development experience on Bitcoin Cash. Once the fee estimation and UTXO selection friction points are polished, XO will be an outstanding framework for production covenants.
